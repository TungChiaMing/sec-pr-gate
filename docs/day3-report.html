01問題

沒有 baseline diff 的 gate 活不過第一天

D2 之後 pipeline 已經會掃、會上傳、會呈現。但要真的擋 PR，還缺一件事：知道哪些 finding 是這個 PR 帶進來的。

一個有五年歷史的 repo，第一次接上掃描器可能吐出 300 筆 finding。如果 gate 對總數設門檻，check 會永遠是紅的 —— 開發者的理性反應不是去修那 300 筆，而是把這個 check 關掉。所有商用產品（Semgrep AppSec Platform、GitHub code scanning、DefectDojo）走的都是同一條流水線：

輸入兩種 JSONSemgrep + Trivy（三種子結構）
→
normalize統一 schema語言無關、工具無關
→
fingerprint穩定識別鍵不含行號
→
storeSQLite冪等、可重跑
→
diffhead − base只對新增的做決定

findings.py 只用 Python 標準函式庫（json / sqlite3 / hashlib / argparse）。這是刻意的：D5 要把整套做成 reusable workflow，任何 consumer repo 都不該為了用這個 gate 而多裝東西。

02schema

一張表吃下四種東西

Semgrep 與 Trivy 的 JSON 是完全不同的結構，而 Trivy 自己又分 Vulnerabilities / Secrets / Misconfigurations 三種。統一之後長這樣（藍色是 fingerprint 的組成）：

toolsemgrep / trivy
categorysast · sca · secret · misconfig
rule_idcheck_id / RuleID / AVDID
path正規化後的相對路徑
pkg套件名（SCA）
cveCVE 編號（SCA）
snippet壓縮空白後的程式碼
severity統一四級
line / end_line顯示用，不進指紋
installed_version現用版本
fixed_version修好的版本
title / messageCWE / PrimaryURL
raw原始 JSON 物件

severity 統一成 CRITICAL / HIGH / MEDIUM / LOW（Semgrep 的 ERROR→HIGH、WARNING→MEDIUM、INFO→LOW），policy 才能用一個門檻寫完。raw 保留原始物件，D4 的 agent 要 Semgrep 的 CWE metadata 或 Trivy 的 PrimaryURL 時直接取，不用回頭解析兩種格式。

severity 對齊不是無損的。Semgrep 的 ERROR 與 Trivy 的 HIGH 是兩套獨立的評分體系，硬映射成同一級會丟掉資訊。這裡接受這個損失，因為 gate 需要單一門檻；真正的嚴重度判斷留給 D4 的 agent，它看得到 raw 裡的完整脈絡。
Q1指紋

為什麼 fingerprint 刻意不含行號？

短答

因為在檔案上方插入程式碼，會讓下方每一筆 finding 的行號位移。含行號的指紋會把所有舊 finding 判成新的 —— gate 會在一個只加了三行註解的 PR 上爆掉。

指紋的組成是 sha256(tool | category | rule_id | path | pkg | cve | 正規化 snippet | ordinal) 取前 16 個 hex。三個設計決定：

  • snippet 先壓縮空白 —— 重新縮排、格式化不算變更
  • ordinal 區分同一檔案內完全相同的兩段程式碼
  • path 要正規化 —— 本機掃 /src、CI 掃 .、base 掃 base/，三者要收斂成同一個字串

Semgrep CE 的 JSON 雖然有 extra.fingerprint 欄位，但值是字串 "requires login"（1.176.1 實測），所以必須自己算。GitHub Code Scanning 的 SARIF partialFingerprints 走的是同一個思路。

發現一

跨語言覆蓋率不對等

同一個 SSRF 漏洞，Python 版被 ssrf-requests 抓到，JS 版完全沒有規則命中。這是 false negative，不是誤報 —— D6 的 recall 分母裡就少了這一筆。

「加 ruleset 就會變好」是要驗證的假設，不是前提。

發現二

誤報是 ruleset 的函數

設計的兩個情境型 FP 都沒觸發，反而多出一個沒設計的。FP 的組成取決於 ruleset，不取決於程式碼。

所以 D6 的 golden labels 必須綁定 ruleset 版本，換一組規則就要重新標。

發現三：規則的框架歸因不可信，兩種語言都一樣。eval 那條是 javascript.browser.security.eval-detected，打在 Node 程式上；D1 則是 python.django.* 打在 Flask 上。D4 的 prompt 要教 agent：rule id 的框架前綴只是分類標籤，判斷要看實際 import 與呼叫關係。

順帶一提：掃描器被自己的規則掃到。Trivy 抓到 repo 根目錄自己的 Dockerfile 有 DS-0001（FROM aquasec/trivy:latest）—— 這正是 D2 報告裡寫的「還沒補上的一刀」。而 DS-0002（root user）沒命中，因為有 USER scanner。防線有效與否，同一個檔案上同時有正反兩面的證據。
Q2量級

為什麼不能直接對總數設門檻？

短答

因為 SCA 的量級跟人的注意力不在同一個數量級。這個 repo 裡，axios@0.21.1 一個過期套件就貢獻了 30 筆 CVE。

來源Findings性質
axios@0.21.130一個 2021 年的套件，HIGH 11 / MEDIUM 18 / LOW 1
app/requirements.txt25D1 就存在的既有債務
testdata/12測試 fixture，含全部 3 個 PyYAML CRITICAL
這個 PR 真正新增的3都在 app/app.py 的 eval 那幾行

94 比 3。如果 gate 看的是總數，開發者每次都要在 94 筆裡找出跟自己有關的那 3 筆 —— 這件事做兩次就沒人做了。差集把訊噪比從 3 % 拉到 100 %。

另一個 D2 就浮現、今天更明確的問題：全部 4 個 CRITICAL 裡有 3 個在 testdata/，真正的 app/ 一個 CRITICAL 都沒有。severity 單獨看會把 gate 導向錯的地方，所以 D5 的 policy.yml 必須帶路徑維度，而不是只有等級門檻。

Q3去重

跨工具的「同一件事」為什麼刻意不合併？

短答

因為「這兩筆是不是同一個問題」本身就是需要判斷的事。tool 是指紋的一部分，所以同一把 key 被 Semgrep 與 Trivy 抓到會是兩筆 —— 合併留給 D4 的 agent。

這個 repo 裡有兩把假的 Stripe key，各被兩個工具抓到，正規化後是 4 筆 secret：

檔案工具rule_idseverity
app/app.py:15Semgrepgeneric.secrets...detected-stripe-api-keyHIGH
app/app.py:15Trivystripe-secret-tokenCRITICAL
server.js:10Semgrepgeneric.secrets...detected-stripe-api-keyHIGH
server.js:10Trivystripe-secret-tokenCRITICAL

看起來明顯該合併，但注意兩邊的 severity 不一樣（HIGH vs CRITICAL），rule_id 與偵測邏輯也不同。機械式合併必須決定「保留誰的 severity」，而那個決定沒有正確答案 —— 它取決於你更信任哪個工具在這類問題上的判斷。

更棘手的是同一工具內的重複：app/app.py:31 一段 SQL 字串拼接被 4 條 Semgrep 規則同時命中，:40 被 3 條。這些是同一個漏洞，但 rule_id 不同、信心不同、建議的修法也不同。

所以 D3 的立場是：正規化層只負責讓資料可比較，不做語意判斷。去重需要「這兩筆講的是不是同一件事」的推理，那是 D4 agent 讀得懂上下文之後才有辦法做的事 —— 而且它做完要能說明理由，機械規則做不到。

05取捨

baseline 怎麼來

三個方案，選了最笨但最可靠的那個：

選用
同一個 run 裡把 base commit 再掃一次
本機用拋棄式 git worktree，CI 用 actions/checkout 到 base/。deterministic、不依賴任何歷史 artifact，consumer repo 的第一個 PR 就能用。代價是掃描時間 ×2（這個 repo 幾十秒）。
替代 A
把 main 的結果存成 artifact 跨 run 下載
省時間，但要處理 retention 過期與「找不到 artifact」的 fallback。今天證明了指紋跨環境穩定，這條路 D5 可以重新評估。
替代 B
Semgrep 原生 --baseline-commit
只涵蓋 Semgrep，Trivy 沒有對應功能 —— 違反「工具無關」這個前提。

pull_request 事件的 checkout 拿到的是 refs/pull/N/merge，也就是合併之後的樹；base 是 github.event.pull_request.base.sha。所以 new = base 沒有、合併結果有 的 findings —— 正好就是 gate 該擋的定義，而 PR 順手修掉的舊 finding 會落在 fixed。

冪等性

PRIMARY KEY (run_label, fingerprint) 加 INSERT OR IGNORE，重新 ingest 同一個 run 會先 DELETE 再寫。實測連跑兩次數字完全相同 —— CI 重跑不會累積髒資料。

06指令

全部走 Docker

make lock       # 產生 package-lock.json（不裝 node_modules）
make scan       # head：掃整個 repo，只產資料不做門檻
make baseline   # base：拋棄式 worktree 裡掃 BASE_REF
make diff       # normalize + fingerprint + 算差集

make findings ARGS="show --run head --category secret"

lock / baseline / diff / findings 都是 image 的 entrypoint 子命令，node、npm、semgrep、trivy 全在容器裡 —— 本機不用裝任何東西。repo 掛成讀寫（要寫 out/、lock 檔、.git 的 worktree），只有 lint-ci 維持唯讀掛載。

make scan 從 D3 起不再做門檻判定 —— 掃描步驟只負責產生資料，決策留給 D5 的 policy.yml。舊的門檻行為保留在 make gate。
