01專案是什麼

一個可攜的 PR 安全掃描閘門

目標不是「多找幾個漏洞」，而是讓安全掃描變成 PR 流程裡一個穩定、可重現、會擋人的步驟。三件事：把工具鏈釘進 image，讓本機與 CI 跑出同一份結果；把兩個工具的輸出合成一份人看得懂的 summary.md；用可調的 severity 門檻決定這個 PR 過不過。

inputPR / repo唯讀掛載到 /src
→
sastSemgrepp/default · p/secrets · p/owasp-top-ten
sca + secretsTrivyvuln · secret · misconfig
→
output/outJSON · SARIF · summary.md
→
gate門檻判定exit 1 → 擋 PR，gh 回貼留言

刻意設計的地方：掃描標的與工具是分離的。/src 是唯讀掛載，換一個 repo 只要換 TARGET；/cache 讓 Trivy 的漏洞 DB 不用每次重抓；門檻用環境變數控制，所以同一個 image 在本機可以只產報告、在 CI 可以擋 PR。SARIF 是為了之後餵給 GitHub Code Scanning。

為什麼標的是一個刻意寫爛的 Flask app：要驗證「掃描器有沒有在做事」，需要一份已知答案的樣本。app/app.py 裡有 4 個真漏洞（hardcoded secret、SQLi、command injection、SSRF），另外埋了情境型誤報——yaml.load 已經用 SafeLoader、md5 只是拿來做 cache key。這份 ground truth 是後面用 LLM 做 triage 時量 precision / recall 的基準。

Q1觀念

SAST 與 SCA 差在哪？為什麼兩個都要跑

短答

SAST 找你自己寫出來的漏洞，SCA 找別人寫的。兩者的輸入、方法、誤報結構都不同，互相補不了。

SAST · Semgrep

分析原始碼的模式與資料流

把程式碼 parse 成 AST，比對「使用者輸入是否流進危險 sink」——例如 request.args 流進 SQL 字串。找的是你這次 PR 寫進去的邏輯缺陷。

  • 誤報高：規則看的是模式，不是語意
  • 需要 triage，這是 agent 的施力點
  • 新程式碼一寫出來就能掃，不必等有人公布漏洞
SCA · Trivy

比對套件名稱 + 版本與漏洞資料庫

讀 requirements.txt 這類 lock/manifest，拿 urllib3@1.26.18 去 OSV / NVD / GHSA 查有沒有登記的漏洞。找的是你相依的別人的程式碼。

  • 誤報低：版本比對幾乎是機械式的
  • 但「有 CVE ≠ 可被利用」——這叫 reachability
  • 版本必須 pin（==）才比得到

實務上絕大多數專案的程式碼有 90% 以上是相依套件，只跑 SAST 等於放掉大部分攻擊面；反過來只跑 SCA，你自己寫的那行 "... WHERE name = '%s'" % name 永遠不會被發現，因為它不在任何漏洞資料庫裡。

兩邊的誤報是不同性質的，處理方式也不同。SAST 的誤報是「這個模式在這個上下文其實安全」——要看周圍程式碼才能判斷。SCA 的誤報是「這個 CVE 存在，但我的呼叫路徑碰不到它」——要看有沒有實際呼叫到脆弱的函式。兩者都是 LLM agent 可以介入的地方，但問的問題不一樣。
Q2供應鏈

GitHub Actions 為什麼要 pin commit SHA，不能用 tag

短答

tag 是可變的指標，commit SHA 是內容雜湊。維護者——或偷到 token 的攻擊者——可以把 v1 指到任何一個 commit，而你的 workflow 不會有任何感覺。

uses: aquasecurity/trivy-action@v0.36.0 這行的意思不是「用 v0.36.0 這份程式碼」，而是「用 現在 v0.36.0 這個標籤指到的東西」。Git tag 可以被 force-push 覆寫，GitHub Actions 每次 run 都重新解析一次，所以同一行 YAML 昨天跑的跟今天跑的可以是完全不同的程式碼。

這不是假設。2026 年 3 月 19 日，攻擊者用竊得的憑證把 trivy-action 的 77 個 tag 中的 76 個、以及 setup-trivy 的全部 7 個 tag 一次覆寫到含惡意程式的 commit，用來竊取 CI/CD secrets；同時發佈了植入惡意程式的 Trivy CLI v0.69.4（以及 3/22 的 Docker 映像 v0.69.5、v0.69.6）。諷刺的是被拿來當跳板的正是一個安全掃描器——CI 裡本來就有高權限 token 的那種工具。

SHA 是那個 commit 內容的雜湊，改內容就換 SHA，沒有辦法「把 SHA 指到別的地方」。所以寫法是把版本號降級成註解：

- uses: aquasecurity/trivy-action@v0.36.0            # tag：可被覆寫
+ uses: aquasecurity/trivy-action@dc5a429b52fcf669ce959baa2c2dd26090d2a6c4  # v0.36.0

代價是不會自動拿到更新，所以要配 Dependabot 或 Renovate——它們認得後面那個註解，會連 SHA 帶註解一起發 PR 升版。組織層級還可以用 GitHub Actions policy 直接強制 SHA pinning，讓沒 pin 的 workflow 根本跑不起來。

同一個道理往外推：Docker image 也要用 digest（image@sha256:…）而不是 :latest。這個 repo 的 Dockerfile 目前用 FROM aquasec/trivy:latest，是還沒補上的一刀。

Q3LLM triage

LLM 為什麼能降低 SAST 誤報？限制在哪

短答

因為靜態規則只看模式，看不到語意。md5 用在 cache key 和用在密碼雜湊，在 AST 上長得一模一樣；差別在意圖與上下文，而那正是 LLM 讀得懂的東西。

把這頁第 02 節那兩個 FP 攤開看就很清楚。規則能判斷的是「這裡呼叫了 yaml.load」「這裡呼叫了 hashlib.md5」；要判斷安不安全，需要的是「Loader 參數是什麼」「這個 hash 的輸出流去哪裡、有沒有被當成信任憑據」。後者是關於資料來源、呼叫關係與可利用條件的推理，不是模式比對。

做法一 · prompting

把上下文塞進 prompt

Datadog 的做法：拿 OWASP Benchmark 當標準答案，把 finding 加上周圍程式碼做成二元分類任務，反覆調 prompt。便宜、可批次，但 LLM 只看得到你餵的那幾行。

做法二 · agent

讓它自己去讀更多檔案

agent 可以追呼叫鏈、開別的檔案、查參數定義。Sifting the Noise（arXiv 2601.22952）在 OSS-Fuzz 資料集上，FP 辨識率從單純 prompting 的 36.4% 提升到 SWE-agent + Claude Sonnet 4 的 95.5%。

差距這麼大的原因不神秘：判斷 app.py:61 的 md5 是不是 FP，需要知道 cache_key() 被誰呼叫、回傳值流到哪裡——那些資訊不在 finding 附近的那 5 行裡，agent 會自己去找，單純 prompting 不會。

限制：過度過濾會壓掉真漏洞。同一篇論文明確警告 aggressive FP reduction 會連真的漏洞一起濾掉——而漏掉一個真漏洞的代價，遠高於讓人多看一則誤報。所以這套東西必須同時量 precision 和 recall，不能只看「噪音少了多少」。另外兩個現實限制：agent 要多讀檔案，token 成本與延遲都比 prompting 高；效果對模型、漏洞類型高度敏感，換一類漏洞就要重新驗證。

務實的落地方式是不要讓 LLM 有刪除權：它只做降級與標註（把 finding 分成「需人看」與「可能 FP，附理由」），門檻判定仍然照原本的 severity 走。這樣最壞情況是多看幾則，而不是漏掉一則。
04指令

怎麼跑

make build      # 建 image（semgrep + trivy + gh）
make version    # 確認 trivy ≥ 0.70.0（不能是被投毒的 0.69.4）

make scan       # 全掃 + 門檻判定，命中即 exit 1（CI 用）
make sast       # 只跑 semgrep，不做門檻判定
make sca        # 只跑 trivy，不做門檻判定
make count      # 不重掃，彙整 reports/ 現有 JSON

TARGET=$(pwd) make scan   # 連 repo 自己的 Dockerfile / workflow 一起掃

make scan 回傳 exit 1 是設計行為，不是執行失敗——FAIL_ON_SEMGREP=ERROR 命中 10 筆、FAIL_ON_TRIVY=HIGH,CRITICAL 命中 8 筆，門檻觸發。要只產報告不擋，把兩個變數設成 none，或用 make sast / make sca。報告輸出在 reports/：semgrep.json、semgrep.sarif、trivy.json、trivy.sarif、summary.md。詳細的 rule id 與 TP／FP 標註在 repo 的 notes.md。
