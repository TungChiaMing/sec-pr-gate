01目標

看得見、可重現、可信任

企業要的不是「有人在筆電上跑過掃描」，而是三件事同時成立：每個 PR 都自動被掃、結果出現在開發者已經在看的地方（PR 頁面 / Security tab）、而且 pipeline 本身不會變成攻擊面。

第三點在 2026 年特別具體。3 月 19 日，攻擊者用竊得的憑證覆寫了 trivy-action 77 個 tag 中的 76 個、以及 setup-trivy 的全部 7 個，並發佈植入惡意程式的 Trivy CLI v0.69.4。任何寫著 uses: aquasecurity/trivy-action@0.28.0 的 pipeline，在下一次 run 就把 CI secrets 送了出去 —— 被當成跳板的，正是一個安全掃描器。

Q1信任鏈

為什麼不直接用 aquasecurity/trivy-action？

短答

因為 pin SHA 只鎖得住 action 的原始碼，鎖不住它執行時去下載的東西。trivy-action 本身就是 3 月被覆寫 tag 的受害者；即使我 pin 到 SHA，它內部仍會再去抓 Trivy binary，那一層我控制不到。

把信任鏈攤開看，用 action 和自己下載的差別在於「我到底在信任什麼」：

用 action
信任 = action 的原始碼 + 它執行時抓的任何東西
pin SHA 之後，第一層鎖住了；第二層仍然是執行期才決定的網路請求。tag 被覆寫時，第一層也曾經整個失守。
自己下載
信任 = GitHub release 上的這一份 bytes
curl release tarball → sha256sum -c 比對寫死在 workflow 裡的值 → 才 install。中間沒有第三方程式碼參與決策。

「checksum 寫死在 workflow 裡」的意思是：我信任的是這個 bytes，不是這個檔名，也不是這個網址。升版時我必須人工去看新的 checksums.txt、把值換掉、送 PR —— 這個摩擦是刻意的。自動升版的方便，換來的就是 3 月那種「下一次 run 悄悄變成別的東西」。

再往上一層還可以做：Trivy 的 release 另附 .sigstore.json，用 cosign verify-blob 可以把信任錨定到 Trivy 專案的 GitHub Actions OIDC identity —— 也就是從「這份 bytes 沒被改」推進到「這份 bytes 確實是 Trivy 的 CI 發出來的」。本週不做，但這是 checksum 之上的正確下一步。

Q2權限

permissions: {} 寫在 YAML，跟 repo settings 設 read-only 差在哪？

短答

兩者都要做，因為它們防的是不同的東西。repo/org 的 default 是保底，但 workflow 檔可以覆寫它；寫在 YAML 裡才會出現在 PR diff，也才能被靜態檢查。

repo / org settings

保底，但看不見

  • 一次設定，涵蓋所有 workflow
  • 但單一 workflow 的 permissions: 可以覆寫它
  • 權限變更發生在設定頁，不會出現在 code review 裡
workflow YAML

可審、可測

  • reviewer 在 PR diff 就看得到權限變化
  • zizmor 這類工具能靜態檢查（excessive-permissions）
  • 跟著 repo 走，fork / 搬遷都不會掉

實際套用的原則是逐 job 最小權限：頂層 permissions: {} 把 GITHUB_TOKEN 整個關掉，然後每個 job 只開它真正需要的。

Job權限為什麼需要
sastcontents: read
security-events: write		checkout PR head；上傳 SARIF
scacontents: read
security-events: write		同上
summarycontents: read只 sparse-checkout scripts/

沒有任何一個 job 拿到 contents: write。Day 5 要寫 PR comment 時才會加 pull-requests: write，而且只加在那一個 job。另外所有 checkout 都設了 persist-credentials: false，避免 token 留在 .git/config 被後面的步驟讀走 —— 這一條在 D1 那個舊 workflow 沒設，zizmor 直接報 artipacked。

Q3gate

SARIF 上傳之後，PR 上看到 alert 就等於 gate 了嗎？

短答

不是。Code Scanning 只是呈現層。要擋 merge 得用 branch protection / ruleset 把某個 check 設成 required；而且 Code Scanning 的 PR 檢查預設只對「新增且達門檻嚴重度」的 alert 亮紅。

這個 PR 剛好把兩者的差別演出來了。pr-security 的三個 job 全綠（我們今天不擋），但 GitHub 從 SARIF 產生的 Semgrep OSS check 是紅的 —— 因為 PR 引入了新的 error-severity alert（eval() 那個 RCE）。紅歸紅，什麼都沒被擋住，因為沒有任何 branch protection 規則把它列為 required。

所以「PR 上有紅勾」和「PR 不能 merge」是兩件獨立的事。本專案把 gate 拆成四段，理由是讓判斷邏輯留在 repo 裡：

Day 2
產生資料
Semgrep + Trivy 各出 JSON 與 SARIF，掃描步驟一律 exit 0
Day 3
算差集
用 fingerprint 算出「PR 相對 main 新增的 findings」—— 今天靠肉眼比對，之後要變成程式
Day 4
判 TP / FP
agent 讀周圍程式碼與呼叫關係，判斷這個 finding 在這個上下文可不可利用
Day 5
決定 exit code
依 policy.yml 決定過或不過，再把這個 job 設為 required check

這樣 gate 的邏輯是可版控、可測試、code review 看得到的，而不是藏在 GitHub 的設定頁裡 —— 沒有人記得那頁上次是誰改的、為什麼改。設定頁只負責一件最單純的事：把 Day 5 那個 job 標成 required。

Day 5 會遇到的衝突：屆時 PR 上會有兩個東西同時表態 —— 我們自己的 policy gate，和 GitHub Code Scanning 的 check。兩者的判準不同（前者看 agent 判過的 TP、後者看 severity），所以必須決定誰說了算，或者把 Code Scanning 的觸發等級調開。這個問題今天就浮現了，早點看到反而省事。
